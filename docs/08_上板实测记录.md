### 板上执行 Python 的唯一正确姿势

```bash
echo xilinx | sudo -S -p '' bash -lc 'cd /boot && python3 xxx.py'
```

三个条件缺一不可：

1. **root** —— 否则 `OSError: Root permissions required`（PL 需要 `/dev/mem`）；
2. **登录 shell `bash -lc`** —— 才会 source `/etc/profile.d/pynq_venv.sh`，把
   `/usr/local/share/pynq-venv/bin` 放到 PATH 最前面。直接 `sudo python3` 会用到
   `/usr/bin/python3`，报 `ModuleNotFoundError: pydantic`；
3. **不能只给 venv python 而不给登录 shell 环境** —— 会报 `RuntimeError: No Devices Found`。

## 3. 上板实测数据（100 MHz）

### 3.1 准确率与批大小无关

`bench.py`，42 张，每种批大小重复 5 次取最好：

| BATCH | 正确/总数 | 准确率 | 墙钟 µs/张 | DMA hw µs/张 |
|---|---|---|---|---|
| 1 | 37/42 | 88.10% | 722.50 | **75.85** |
| 2 | 37/42 | 88.10% | 367.84 | 38.73 |
| 4 | 37/42 | 88.10% | 195.83 | 19.79 |
| 8 | 37/42 | 88.10% | 115.63 | 15.54 |
| 21 | 37/42 | 88.10% | 50.68 | 12.01 |
| 42 | 37/42 | 88.10% | 35.01 | **11.47** |

**六种批大小的结果逐样本完全相同**，都是已知的 5 个错分样本（22/24/26/41/42）。
这是"批处理没有改变任何一张图的推理结果"最直接的证据。

> `bt.py` 的判定是"整批全对才算 OK"，所以只要批里含那 5 个样本就会报 `BAD`。
> 看到 `BAD` 时不要误判为功能错误，必须按样本计数核对。

### 3.2 B=42 的独立复核（bench2.py）

输入缓冲区只填一次，计时窗口内只有 `dma.transfer`：

```
正确          : 37/42 (88.10%)
DMA 内部 hw   :    478.1 us  -> 11.38 us/sample   (MM2S 374.9 + S2MM 103.3)
墙钟 (仅传输) :    834.0 us  -> 19.86 us/sample
两者之差      :    355.8 us  (flush / invalidate / 轮询)
```

### 3.3 时间的三个层次（不要混用）

| 口径 | B=1 | B=42 | 说明 |
|---|---|---|---|
| 硬件传输 hw | 75.85 µs | **11.38 µs** | 写 MM2S_LEN → S2MM IOC，纯 PS→PL→PS |
| 含 cache 维护 | ≈76 µs | 19.86 µs | 加 `in_buf.flush()` / `out_buf.invalidate()` |
| 含脚本数据准备 | 722.5 µs | 35.01 µs | 再加 `in_buf[:] = bytearray` 的 numpy 转换（约 600 µs/批，可优化） |

**对外汇报用第一行**：75.85 → 11.38 µs/张，6.7×。
第二、三行是 Python 侧开销，不是 PL 的能力，但评分若按"跑完 42 张的总时间"计，就要看第三行。

### 3.4 板上 PL 的真实时钟（重要）

读 PS7 的 FPGA0 时钟控制寄存器 `0xF8000170`：

```
val = 0x00200400   srcsel = 0 (IO PLL 1000 MHz)   div0 = 4
```

**结论：BD 里的 `FCLK0` 频率只影响时序约束，不改变板上真实频率。**
Zynq 的 PS 时钟由启动时 FSBL 配置好，换比特流不会改它。

独立佐证：仿真给出每张样本 **1339 个计算时钟周期**，而 B=42 实测 42 张共 478.1 µs
（11.38 µs/张）。若真跑 100 MHz，每张至少 13.39 µs、42 张 ≥ 562 µs —— 实测更快，
说明真实时钟明显高于 100 MHz（约 118 MHz 以上）。

由此得到两条必须记住的推论：

1. **性能数字与 BD 里写的频率无关**，100 MHz 版实测 75.85 µs 与 Lab8 的
   125 MHz 版 75.75 µs 几乎相同，就是这个原因。
2. **时序约束必须设在真实频率上（8 ns），否则 WNS 是假的**。
   100 MHz 版 WNS +0.746 @ 10 ns 意味着关键路径 9.25 ns，在真实频率下并不满足。

### 3.5 批处理为什么有效

`dma_probe.py` 的结论：MM2S 传输 **8 字节与 520 字节耗时基本相同**（≈46 µs），
S2MM 同样有 ≈30 µs 固定开销。即每笔 AXI DMA 传输的成本与数据量几乎无关。
B=42 把 42 笔合并成 1 笔，固定开销摊薄到 1/42。

## 4. 本次修掉的关键 bug（会静默毁掉批处理）

### 4.1 `batch_left` 多驱动

错误写法：`batch_left <= 8'd1;` 放在**输出数据寄存器**那个 `always` 块的复位分支里，
而载入/递减在 **FSM** 的 `always` 块里 —— 同一个 reg 被两个块驱动。

综合报告：

```
[Synth 8-6859] multi-driven net on pin Q with 1st driver pin
               'inst/u_fc_top/batch_left_reg[7]__0/Q'   fc_top.v:155
[Synth 8-6858] multi-driven net Q is connected to at least one constant driver
               which has been preserved, other driver is ignored
```

后果：最高位被常量顶掉，`batch_left == 8'd1` 判据不可靠，`tlast` 可能永不产生，
S2MM 直接挂死。**仿真不报错，只有综合日志里这一条。**

修法：把 `batch_left <= 8'd1;` 移进 FSM 块的复位分支，原位置留注释。
修复后新 `runme.log` 中 `multi-driven` / `8-6859` 计数 = **0**，仿真 4 包 / 12 包连发全过。

### 4.2 防复发的门禁

`_work/full_rebuild.tcl` 在综合后强制打印并核对：

```tcl
puts "BATCH_CELLS = [llength [get_cells -hier -filter {NAME =~ *batch_left*}]]"   ;# 期望 25
foreach lg [glob .../*synth_1/runme.log] { ... 搜 "multi-driven net" ... }        ;# 期望无输出
```

## 5. 环境坑（这台机器上 Vivado 2022.1 的实际行为）

| 现象 | 根因 | 对策 |
|---|---|---|
| `create_bd_design` 报 `couldn't read file "replace_bd_cell.tcl"` | xgui 子解释器初始化失败 | **必须 `-mode gui`**，batch 模式必挂 |
| `open_bd_design` 报 `failed due to earlier errors` | `E:/Xilinx/Vivado/2022.1/tps/tcl/tcllib1.11.1/math/bignum.tcl` **不存在**，`package require math::bignum` 失败，PS7 时钟面板的 `clock_temp` 建不出来 | **不要开 BD**：直接在 `design_1.bd` 里改 JSON 参数 |
| `generate_target {… hw_handoff}` 失败 | `hw_handoff` 会实例化 `clock_temp`，同上 | 只用 `{synthesis implementation}`；`.hwh` 在 BD 构建阶段已生成 |
| `generate_target all` / `{… simulation}` 失败（`missing close-bracket`） | PS7 的 System C Simulation 产物 | 同上，别加 `simulation` / `all` |
| `generate_target` 返回成功但产物时间戳不变 | Vivado 认为输出产物是新的，不重生成 —— **PS7 还是 100 MHz** | 先 `reset_target {synthesis implementation}` 再生成，并**校验生成的 xdc** |
| `[Vivado 12-4739] create_clock: No valid object(s) … s_axis_aclk` / `[Constraints 18-4644]` | `lab8c.xdc` 是给 IP 级 OOC 写的，整机顶层 `design_1_wrapper` 没有这些端口 | 无害。Lab8 已验证构建同样存在（13~22 次），WNS 仍收敛 |
| `[Synth 8-6895] reference checkpoint … not suitable for incremental` | 早期失败运行残留的 `utils_1/imports/synth_1/pl_fc_top.dcp` 被当增量参考 | 删除该文件；Vivado 会自动退回全量流程，结果不受影响 |

### 时钟频率参数实际驻留在三个地方（本次最大的坑）

同一个 `PCW_FPGA0_PERIPHERAL_FREQMHZ` 在工程里存了 **三份**，改错了地方等于没改：

| 位置 | 作用 | 改法 |
|---|---|---|
| `design_1.bd`（JSON） | BD "图纸"，**不直接生效** | 手改 JSON 只影响下次打开 BD 的界面显示 |
| `.../bd/design_1/ip/design_1_processing_system7_0_0/*.xci` | **真正的参数载体**，`generate_target` 按它出网表 | 用 `set_property CONFIG.PCW_FPGA0_PERIPHERAL_FREQMHZ {125} [get_ips ...]` |
| 生成物 `ps7_parameters.xml` / `ps7_init.c` / `*.xdc` | 综合和比特流实际用的值 | 由上一行自动重出，**不要手改** |

本次踩到的完整链路：

1. 只改 `.bd` → `generate_target` 返回成功、产物时间戳也变了，但 PS7 还是 100 MHz
   （因为 `.xci` 没变）；
2. `reset_target` + `generate_target` 仍然无效，理由同上；
3. 最后用 `set_property` 改 IP 实例参数 → `.xci` 同步 → 生成物才是 125。

**唯一可信的判据**：生成出来的 `ps7_parameters.xml` 里

```xml
<PARAMETER NAME="PCW_FPGA0_PERIPHERAL_FREQMHZ" VALUE="125" />
<CLOCKOUT NAME="FCLK_CLK0" FREQUENCY="125.000000" />
```

以及综合后 `get_property PERIOD [get_clocks clk_fpga_0]` 必须是 **8 ns**。
脚本 `_work/rebuild_125d.tcl` 在综合后、实现前设了这道硬门禁，不满足直接 `exit 1`。

### 时钟频率的硬门禁（血的教训）

`build_bd.tcl` 里默认写的是 **100 MHz**，而 Lab8 的 `.bd` 后来被改成 **125 MHz**。
干净工程重建后会"悄悄退回" 100 MHz。必须在综合前校验：

```tcl
set xdc ".../design_1_processing_system7_0_0/design_1_processing_system7_0_0.xdc"
regexp {create_clock -name clk_fpga_0 -period "([0-9.]+)"} [read [open $xdc]] -> per
if {$per ne "8"} { puts "ABORT: not 125 MHz"; exit 1 }
```

否则会在 100 MHz 的比特流上算出"很好看"的 WNS（+0.746 @ 10 ns），毫无意义。

## 7. PS 侧优化（2026-11-22 已完成并实测）

`lab8_npu.py` 做了四处改动，全部在板上验证通过（仍是 88.10%，特征图逐字节一致）：

| 改动 | 原因（实测数据） | 效果 |
|---|---|---|
| `BATCH` 1 → 42（可用 `LAB8_BATCH` 环境变量覆盖） | 每笔 DMA 有 46 µs MM2S + 30 µs S2MM 固定开销 | 硬件 75.85 → 11.59 µs/张 |
| 样本改用 numpy 预排 + `np.copyto` | `in_buf[:] = bytearray` 填 21 KB 要 155 µs | → 51 µs |
| SA/DA 寄存器只在缓冲区变更时写 | 单次 AXI-Lite 寄存器写实测 **4.4 µs**，原来每笔传输写 6 次 | 每笔 6 写 → 2 写 |
| `.coe` 改成字符级 numpy 过滤 | 逐 token `strip()/set()` 解析 21,504 个 token 要 360 ms | 361 ms → 179 ms |

实测分段（`python3 lab8_npu.py`）：

```
[t] overlay 加载        1708.0 ms     ← 4 MB 比特流 + hwh 解析，固有
[t] DMA 驱动初始化          3.0 ms
[t] 读样本/标签           178.6 ms     ← 优化前 361 ms
[t] 分配 DMA 缓冲           4.7 ms
[t] 42 张推理（1 笔 DMA）    3.3 ms     ← 其中硬件 486.6 us，其余是 42 行打印
[t] 特征图读取              3.6 ms
进程总耗时 1901.9 ms，其中推理 0.5 ms
```

> 注意 `time` 显示的 12.4 s 与进程内 1.9 s 的差额是 `import pynq` + numpy 的
> 固有导入时间（`user 11.1 s`），与设计无关。

**时间口径建议对外这样说**：
- "**每张 11.6 µs**（42 张一次 DMA 的硬件传输时间）"—— 这是设计能力；
- 若被问"跑完整个脚本要多久"，答"约 2 s，其中 1.7 s 是加载比特流、0.18 s 是读样本，
  真正推理 0.5 ms"。

## 8. 125 MHz 版本的上板复测（最终数据）

用 `49d4e6d7…` 这个比特流重跑一遍，所有指标与 100 MHz 约束版一致：

```
accuracy      = 37/42 = 88.10 %

  fc1[0:8] = [4, 1, 0, 0, 0, 0, 0, 0]

```

批大小扫描（`bench.py`，125 MHz 版）：

| BATCH | 正确/总数 | 准确率 | 墙钟 µs/张 | DMA hw µs/张 |
|---|---|---|---|---|
| 1 | 37/42 | 88.10% | 706.16 | 81.35 |

> **11.538 与 100 MHz 约束版的 11.586 几乎相同**——这反过来证实第 3.4 节的结论：
> BD 里的频率设定只影响时序约束，不改变板上真实运行频率。
