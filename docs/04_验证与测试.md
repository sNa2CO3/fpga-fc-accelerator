# 04 验证与测试

[← 返回总览](00_项目总览.md)

> 本篇回答一个问题：**凭什么说这个设计是对的？**
> 答案是三层互相独立的证据链，任何一层出错都会被发现。

---

## 1. 验证策略：不自己验证自己

```
        ┌─────────────────┐
        │ 官方参考文件      │  fc1.txt / fc2.txt / fc3.txt / int8_results.txt
        └────────┬────────┘
                 │ ① 逐值比对
        ┌────────▼────────┐
        │ Python 独立模型  │  完全不用 RTL, 从原始 coe 复算
        └────────┬────────┘
                 │ ② 逐值比对
        ┌────────▼────────┐
        │ RTL 行为级仿真   │  xsim
        └────────┬────────┘
                 │ ③ 逐字节比对
        ┌────────▼────────┐
        │ 上板结果         │  PS 端 42 个样本
        └─────────────────┘
```

**关键点**：Python 模型和 RTL 是**两套独立实现**（一个用 Python 整数运算，
一个用 Verilog 时序逻辑），它们都和官方参考对上，才说明设计真的对。

## 2. 各级验证的实测数字

### 2.1 Lab4：第一层（512→128）

| 检查 | 结果 |
|---|---|
| fc1 输出 vs `fc1_ref.txt` | **128/128 一致** |
| 加法树单元测试（全负/混合/全 1 × 3 配置） | **9/9** |
| 延迟链常数 `L_RAM=3` 的锚定 | 由第一层比对反推确认 |

> Lab4 的价值不只是"第一层能算"，更是**把 `L_RAM` 这个全局最危险的常数实测锚定了**。
> `.xci` 里写 `C_READ_LATENCY_A=1`，实际行为是 3——信了文档就全错。

### 2.2 Lab5：三层网络

| 检查 | 结果 |
|---|---|
| fc1 / fc2 / fc3 vs 官方参考 | **128/128、32/32、2/2** |
| Python 独立复算 vs 官方参考 | **26 项全过** |
| 最终实现 | DSP 152、WNS +1.127 ns、0 失败端点 |

### 2.3 Lab6：截位（最严格的一轮）

| 检查脚本 | 项数 | 结果 |
|---|---|---|
| `analyze.py`（Python 独立复算 + 截位推导） | 18 | **18/18** |
| `make_coe.py`（打包 coe + 回读校验） | 7 | **7/7** |
| `check_sim.py`（RTL 仿真 vs Python 模型） | 14 | **14/14** |
| `audit_acceptance.py`（验收自查） | 37 | **37/37** |

其中最有说服力的一条：

```
RTL 仿真 vs Python 模型：13 608 个值逐一相同
   fc1: 42 样本 × 128 = 5 376
   fc2: 42 × 32        = 1 344
   fc3: 42 × 2         =    84
   两个位宽（8bit / 4bit）各一套
```

还有一个"不可能作弊"的检查：

```
[A3] fc1_w4[i] == fc1_w8[i] >> 4   对全部 5 376 个值成立
```

4bit 与 8bit 的 fc1 输入和权重完全相同，只有 `SH1` 不同（14 vs 10）。
如果 4bit 变体没真正生效，这个关系不可能成立。

### 2.4 Lab7：数据流控制

| 轮次 | 样本 | 模式 | 结果 |

| 2 | 样本 1 | 特征图 | 162 字节全对 ✓ |

### 2.5 Lab8：AXI-Stream 与跨时钟域

| 轮次 | 时钟关系 | 样本 | 结果 |
|---|---|---|---|
| A | axi 100 MHz / fc 100 MHz（同频） | 样本 1 | 推理 + 162 字节特征图 ✓ |
| B | axi 100 MHz / **fc 150 MHz**（真跨域） | 样本 23 | 推理 + 162 字节特征图 ✓ |

B 轮是专门为验证异步 FIFO 设计的：两个时钟不同频，如果 CDC 有问题，
数据会错位或丢字，特征图立刻对不上。

## 3. 验证发现的真实 bug（答辩时可以用来证明"验证有效"）

| # | 现象 | 根因 | 发现方式 |
|---|---|---|---|
| 1 | 加法树输出全 `x` | 顶层节点取成 `node[NUM_INPUTS-1]`，实际是 `node[NUM_INPUTS-2]` | 单元 testbench |
| 2 | 加法树负数全错 | `data[k*DW +: DW]` 是无符号部分选择，没做符号扩展 | 全负输入单元测试 |
| 3 | fc1 只有 102/128 对 | 车道约定混用（老师给的 coe 是 MSB 优先，自己生成的是 LSB 优先） | 逐值比对 |
| 4 | 综合后 71 个 LUT、0 个 DSP | 数据通路不可观测，被综合器当死逻辑删掉 | 综合报告异常 |
| 5 | 布局布线 IO 失败 | 三层输出共 164 bit > CLG400 的 125 个用户 IO | place_design 报错 |
| 6 | 8bit 综合实际是 4bit | 上一版脚本残留在 run 上的 `-generic CUT_W=4` 覆盖了 wrapper 参数 | 审计脚本比对 synth 命令行 |
| 7 | 推理结果字节反了 | fc3 两个通道比较写反（特征图全对、只有结果错） | Lab7 分层验证 |
| 8 | AXI 版特征图全错 | testbench 打包字节序写成 LSB 优先，与 fc_top 的 MSB 优先不一致 | Lab8 仿真 |
| 9 | FIFO 吃掉 3.7 万个触发器 | 复位时 for 循环清零存储阵列，综合不出 BRAM | 综合报告寄存器异常 |

> 第 6、8 两条尤其值得讲：它们都是**"不报错但结果错"**的类型，
> 只有靠"逐值比对 + 审计脚本"才能抓到。

## 6. 仿真波形怎么截（Lab8 报告用）

> 默认打开仿真只有 testbench 顶层的几个信号，看不出 NPU 在干什么。
> 这里给出**要截哪三张、每张看什么、怎么一键加信号**。

### 6.1 一键加信号

跑完仿真后，在底部的 **Tcl Console** 里执行：

```tcl
source D:/VivadoProject/Lab8/scripts/add_waves.tcl
```

波形窗口会按"时钟 → AXI 输入 → NPU 内部 → 打包 → AXI 输出"的顺序排好 **25 个信号**。

> 脚本**会先清空当前波形窗口**——`add_wave` 是"追加"，不清空的话会和 Vivado
> 自动加的调试变量（`in_bytes`、`err_cnt`、`i`、`k`…）叠成几十个，根本看不清。
> 清空后逐个检查信号是否存在，最后打印"已添加 N 个、缺失 M 个"。

> **如果提示"找不到 /tb_pl/npu_state"**：说明当前跑的是**旧快照**。
> 改过 `tb_pl.v` 之后必须点工具栏的 **Relaunch Simulation**（圆形箭头图标），
> 只点 Run All 不会重新编译 testbench。

> **如果波形只到 1 µs 就停了**：是 `xsim.simulate.runtime` 没设够（Vivado 默认 1000 ns），
> 而一次完整仿真要跑到 26.5 µs。工程里已经设成 `40us`；
> 如果打开的是旧工程，在 Tcl Console 里补一句即可：
> ```tcl
> set_property -name {xsim.simulate.runtime} -value {40us} -objects [get_filesets sim_1]
> ```
> 然后 **Relaunch Simulation**。（命令行 `run_xsim.sh` 用的是 `-runall`，
> 会一直跑到 `$finish`，所以不受这个设置影响。）

> testbench 里已经把 NPU 的内部信号**提到顶层**（`npu_state` / `cmd_reg` /
> `fc_dout` / `pk_*` / `fc3_y1` / `fc3_y2`），所以不展开层次也能加。

### 6.2 需要截的三张图

#### 图 1：一次完整推理（样本 1）

**时间范围**：从 `s_tvalid` 第一个上升沿到 `done_o` 脉冲，整包 1339 拍（125 MHz 下 10.712 µs）；
其中三层计算 1144 拍 = 9.152 µs，其余 195 拍是命令、收样本与输出。

| 看什么 | 信号 | 应看到 |
|---|---|---|
| 输入包 | `s_tvalid` / `s_tready` | 连续 **65 拍**握手（1 指令 + 64 样本），最后一拍 `s_tlast=1` |
| 指令被解析 | `cmd_reg` | 从 0 变成 **1**（0x01 = 推理） |
| 状态流转 | `npu_state` | `0 → 1 → 2 → 3 → 4 → 5 → 8 → 0` |
| 输出 | `m_tvalid` / `m_tlast` | **1 拍**，`m_tlast=1`，`m_tdata[7:0] = 00`（分类结果 0） |

> 这张图是"系统跑通了"的核心证据：从 PS 发数据到 PS 收到结果，全链路一张图看完。

#### 图 2：特征图输出（样本 1）

**时间范围**：第二个指令（`cmd_reg = 2`）到 `done_o`

| 看什么 | 信号 | 应看到 |
|---|---|---|
| 指令 | `cmd_reg` | 变成 **2**（0x02 = 特征图） |
| 状态走另一条支路 | `npu_state` | `1 → 6 → 7 → 8 → 0`（**注意没有 2/3/4/5**，说明没有重新推理） |
| 逐字节输出 | `fc_dout_vld` | `state=6` 时连续 **128 拍**，`state=7` 时 **32 拍**，`state=8` 时 **2 拍** |
| 打包 | `pk_vld` | 每 8 个 `fc_dout_vld` 出现 1 次 |
| 输出 | `m_tvalid` | **21 拍**，`m_tlast` 只在第 21 拍 |

> 这张图证明"特征图模式不重新推理"——`npu_state` 直接从 command 跳到 FC1_out。

#### 图 3：跨时钟域（样本 23）

**时间范围**：第二段测试（`fc_period_sel = 1` 之后）

| 看什么 | 信号 | 应看到 |
|---|---|---|
| 两个时钟不同频 | `s_axis_aclk` vs `fc_clk_use` | 10 ns 周期 vs 6.67 ns 周期 |
| 数据仍然正确 | `m_tvalid` / `m_tdata` | 推理 1 拍 `01`，特征图 21 拍 |

> 这张图证明异步 FIFO 的 CDC 是对的。如果 CDC 有问题，特征图会错位或丢字。

### 6.3 建议的显示设置

- `npu_state` / `cmd_reg`：右键 → *Radix* → **Hexadecimal**（或 Unsigned）
- `s_tdata` / `m_tdata` / `pk_dout`：**Hexadecimal**（看字节序方便）
- `fc_dout` / `fc3_y1` / `fc3_y2`：先设 **Signed Decimal** 看数值，再切 Hexadecimal 对字节
- 图 1 可以把光标停在 `done_o` 上，读数就是推理时间

### 6.4 如果还想要更细的

## 7. 仿真环境说明

- **工具**：Vivado 2022.1，命令行 `xvlog → xvhdl → xelab → xsim`
  （GUI 的 `launch_simulation` 在 Git Bash 下会 "Broken pipe"，所以走命令行）。
- **必须混合语言**：`mult_gen` 只提供 VHDL 仿真模型，BRAM 模型是 Verilog。
- **BRAM 仿真读 `.mif` 不读 `.coe`**：运行前要把 `.mif` 拷进仿真目录。
- **Vivado Tcl 必须纯 ASCII**：中文路径会被按本地代码页解析而乱码。
