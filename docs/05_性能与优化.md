## 1. 实测指标

|---|---|---|

| Block RAM | 63 / 140（45.00 %） | — |
| Slice LUTs | 12 430 / 53 200（23.36 %） | — |
| Slice Registers | 16 331 / 106 400（15.35 %） | — |
| **功耗（整机）** | **1.653 W**（动态 1.506 + 静态 0.147） | 1.848 W |

> 含 BD 里的 DMA、AXI 互联与 PS7 包装。

### 1.2 准确率与单张推理时间

| 指标 | 本设计 | 说明 |
|---|---|---|
| 分类准确率 | **88.10 %**（37/42） | 与课程 INT8 参考逐样本一致；是这套 INT8 权重的上限 |
| **三层计算**（FC1 1042 + FC2 82 + FC3 20） | **1144 拍 = 9.152 µs** @125 MHz | 纯计算，不含收发；**PPT 与答辩用这个** |
| 单张整包（含命令与收发） | **1339 拍 = 10.712 µs** @125 MHz | 命令 1 + 收样本 192 + 三层 1144 + 输出 2 |
| 单张端到端（B=1，PS→PL→PS） | **75.85 µs** | 见 1.3，瓶颈是 DMA 固定开销而非计算 |

> **两个 PL 指标的差别只有一个**：1144 是三层运算本身，1339 再加上"收 64 个样本字"的 192 拍
> 和命令、输出。写文档时容易把 1339 直接叫成"计算时间"，那就和 PPT 的 9.152 µs 对不上了。

### 1.3 端到端 PS→PL→PS（含批处理，实板实测）

交付指标是 PS→PL→PS 往返时间，不是 PL 计算时间。逐张模式下每笔 AXI DMA
都有约 **46 µs MM2S + 30 µs S2MM** 的固定开销（8 字节与 520 字节耗时几乎相同，
见 `dma_probe.py`），所以**批处理**才是决定性优化：

| 批大小 | 准确率 | DMA 实测 µs/张 | 相对 B=1 |
|---|---|---|---|
| 1 | 37/42 | 75.85 ~ 81.35 | 1.00× |
| 2 | 37/42 | 38.73 ~ 39.93 | 1.96× |
| 4 | 37/42 | 19.79 ~ 20.89 | 3.7× |
| 8 | 37/42 | 15.54 ~ 15.92 | 6.2× |
| 21 | 37/42 | 12.01 ~ 12.11 | 14.2× |
| **42** | **37/42** | **11.38 ~ 11.62** | **6.6×（对硬件）／20.6×（含 PS 开销）** |

**六种批大小的结果逐样本完全相同**，说明批处理没有改变任何一张图的推理结果。

**结论：准确率持平；资源、功耗接近参考；单张推理落后约 1.4 倍，但端到端
经批处理后可做到 11.6 µs/张，劣势被抹平。**

## 2. 时间都花在哪了

1339 拍的构成（testbench 逐状态实测 @125 MHz）：

| 阶段 | 拍数 | 占比 | 能不能压 |
|---|---|---|---|
| 命令字 | 1 | 0.1 % | — |
| 收样本（64 个字） | 192 | 14.3 % | ✅ 可压到 65 |
| **FC1（128 通道 × 8 组）** | **1042** | **77.8 %** | ✅ 只有靠提高并行度 |
| FC2（32 通道 × 2 组） | 82 | 6.1 % | 部分 |
| FC3（2 通道 × 1 组） | 20 | 1.5 % | 已到底 |
| 输出 | 2 | 0.1 % | — |

**FC1 占 77.8 %，是唯一的优化重点。**
其结构是"一个输出通道 × 一个输入组 = 一拍"，所以
`fc1 拍数 = 输出通道数(128) × 组数(8) / 每拍并行通道数`。

## 3. 三条优化路（定量）

### 路线 A：提高并行度（64 车道 → 128 车道）

**做法**：把阵列从 64 路扩到 128 路，一拍同时算 **2 个输出通道**。

| 项 | 64 车道（当前） | 128 车道 |
|---|---|---|
| fc1 拍数 | 1042 | **521** |
| fc2 拍数 | 82 | 41 |
| fc3 拍数 | 20 | 10 |
| 总拍数 | 1339 | **767** |
| @125 MHz | 10.71 µs | **6.14 µs** |
| DSP | 64（29 %） | **128（58 %）** |
| LUT 估算 | ~6.1 k | ~10 k |
| 加法树 | 64 输入 6 级 | 128 输入 7 级 |

**收益**：时间几乎减半（超过参考实现的 7.585 µs）。
**代价**：DSP 翻倍、面积约 +60 %、功耗上升。

**要改的地方**（改起来不难，但要全部重验）：

1. `adder_tree` 参数 `NUM_INPUTS 64→128`（7 级，`WTOP = 16+7 = 23`）；
2. `mult_array_8` 例化 128 次；
3. 三层模块的 `LANES`、`GROUPS`（fc1 8→4，fc2 2→1）、`out_channel` 步进；
4. 层间 RAM 的行宽（512→1024bit）与打包级；
5. **延迟链 `D_TREE = $clog2(128) = 7`，整条链 +1 拍**——这一步最容易错。

### 路线 B：提高时钟频率

| 目标频率 | 周期 | 1339 拍耗时 | 前提 |
|---|---|---|---|
| 100 MHz | 10 ns | 13.39 µs | 历史版本，WNS +0.746 ns |
| **125 MHz** | 8 ns | **10.71 µs** | **最终交付：WNS +0.403 ns，0 失败端点 / 63 279** |
| 150 MHz | 6.67 ns | 8.93 µs | 需要重做关键路径（见下），且 CDC 要重验 |
| 200 MHz | 5 ns | 6.70 µs | 基本不可能 |

> **口径提醒**：BD 里设定的 FCLK 频率只决定**时序约束的松紧**，
> 不改变板上实测运行频率（Zynq 的 PS 时钟由启动时 FSBL 配置）。
> 因此 100 MHz 约束版与 125 MHz 约束版的实板耗时几乎相同
> （11.586 vs 11.538 µs/张）；125 MHz 版的真正价值是**按真实频率做了时序签核**。

**当前关键路径**：

```
u_axis_rd/u_infifo/wr_addr_ptr_reg[5] → FIFO 存储
逻辑级数 0，数据路径 8.771 ns 中布线占 8.315 ns（94.8 %）
```

（这是 OOC 实现下的关键路径：两个 FIFO 因为落在 LUTRAM，写指针扇出很大。
在 BD 里把 FIFO 换成 FIFO Generator 的 BRAM 版本，这条路径会明显缩短。）

**注意：瓶颈不是运算，是布线。** 因为 `fc1_weight_ram` 是 1024bit 宽，
要 ~15 个 RAMB36 并排，地址寄存器要扇出到十几列 BRAM，走线很长。

**修法**（一次就有望到 125~150 MHz）：

```verilog
(* max_fanout = 8 *) reg [8:0] weight_addr_o;   // 让工具自动复制驱动
```
或手工复制几份地址寄存器分别驱动不同 BRAM 列。
代价是几十个 FF，几乎不影响资源分。

### 路线 C：收样本流水化（便宜的小优化）

当前 `S_DATA_RCV` 每个字要 2 拍（发读请求 → 等 valid）。改成持续拉高读使能：

```verilog
din_ready <= ~fifo_empty & ~(din_valid & last_word);   // 每拍都读
```

- 收益：192 拍 → 65 拍，省 **127 拍（−9.5 %）**；
- 风险：低，但要注意"最后一个字不要多读"（否则会把下一条指令读走）。

## 4. 资源与功耗

### 4.1 资源构成

> 下表是**整机**（`design_1_wrapper`，含 BD 的 DMA / 互联 / PS7 包装）的官方报告值。

| 资源 | 占用 | 大头在哪 |
|---|---|---|
| DSP 64 | 29.09 % | 乘法阵列（64 × 1） |
| BRAM 63 | 45.00 % | **宽度**吃的：fc1 权重 1024bit 宽要 ~15 个 RAMB36，输入 RAM 同理 |
| LUT 12 430 | 23.36 % | 加法树 + 控制 + 打包 + **FIFO 存储 1 427** + AXI/DMA 互联 |
| FF 16 331 | 15.35 % | 延迟链 + 打包缓存 + 格雷码指针 + AXI 接口 |

> 两个异步 FIFO 的存储阵列最后落在 **LUTRAM（1 427 个 LUT）**，不是 BRAM。
> 原因是它们的读写分属两个时钟域，Vivado 的 `ram_style="block"` 推断失败
> （会报 `Infeasible attribute`）。用 BRAM 更省功耗，但需要改成
> 真双口 BRAM 的写法（或在 BD 里直接用 FIFO Generator）——留给后续优化。

> BRAM 用掉 43 % 但容量远没用完（权重深度 512，深度方向只用了一半），
> 全是"位宽摊出来的"。如果改成 512bit 行宽（例如 64 车道 × 8bit 存半行），
> BRAM 能降到 ~30 个 tile，但要改地址映射和打包逻辑。

### 4.1.1 提频到 125 MHz 后的实测（已完成）

对 `fc1/fc2/fc3` 的地址寄存器加了 `(* max_fanout = 8 *)`，把"地址寄存器 → 十几个 BRAM 列"
这条纯布线路径拆成多份，再把 BD 的 FCLK 改为 125 MHz：

| 项目 | 100 MHz 约束 | **125 MHz 约束（最终交付）** |
|---|---|---|
| WNS | +0.746 ns | **+0.403 ns**，TNS 0，0 失败端点 / 63 279 |
| 关键路径 | — | `fc_top/FSM_onehot_state_reg[7]` → 乘法阵列 DSP 的 B 口（4 级逻辑，7.6 ns） |
| LUT / FF | 12 425 / 16 316 | 12 430 / 16 331 |
| BRAM / DSP | 63 / 64 | 63 / 64 |
| 功耗 | 1.603 W | **1.653 W（+3.1 %）** |
| **NPU 计算** | 13.39 µs | **10.71 µs（−20 %）** |
| `BATCH_CELLS_IMPL` | — | **25**（批处理逻辑确实进了实现网表） |

> **这是一次典型的"低风险换时间"**：只改了 8 行属性 + 一个时钟频率，
> 不动任何架构，DSP/BRAM 不变，代价是功耗 +3.4 %。
> 时间分（25 %）提升 20 %，功耗分（25 %）损失约 3 %，**净收益为正**。

### 4.2 功耗

Vivado `report_power` 的结果见 `_work/power.rpt`。影响功耗的主要因素：

| 因素 | 影响 | 本设计的取舍 |
|---|---|---|
| 时钟频率 | 线性 | 最终用 125 MHz；与 100 MHz 版相比功耗 +3.1 %，换 NPU 时间 −20 % |
| DSP 数量 | 正比 | 64 个（128 车道路线会翻倍） |
| 翻转率 | 正比 | 输入数据是图像特征，翻转率不高 |
| 时钟树 | 显著 | 两个时钟域同源，实际上只有一棵时钟树 |
| FIFO 存储阵列 | **巨大** | 见下方注意 |

> **一个很容易踩的功耗/面积坑**：Lab3 的 FIFO 在复位时清零整个存储阵列，
> 综合器推断不出 BRAM，会摊成 **6.6 万个触发器**（整片设计的 72 %）。
> 这些触发器每个都要时钟驱动，功耗比 BRAM 高一个量级。
> 去掉清零后只占约 1.5 个 BRAM tile——**这一处修改的功耗收益比调频率还大**。

**时间与功耗是一对矛盾**：路线 A（128 车道）让时间减半但功耗和面积都涨。
25 % : 25 % 的评分权重下，**两者大体抵消**，所以我们的选择是
**保资源/功耗、放弃一部分时间分**——这也是下面要讲的取舍。

## 5. 我们的取舍与理由

| 决策 | 选择 | 理由 |
|---|---|---|
| 并行度 | **64 车道** | DSP 29 %，资源分和功耗分都好看；128 车道会把 DSP 推到 58 %，加权后基本抵消 |
| 时钟 | **125 MHz** | 关键路径靠 `max_fanout` 复制地址寄存器压下来，WNS +0.403 ns，功耗仅 +3.1 % |
| 位宽 | **8bit（三层全截位）** | 准确率零损失（88.10 %），且让三层能共用一套阵列 |
| 加法树 | **精确不截位**（每级 +1 位） | 省下的几位 LUT 换不来准确率，没必要冒险 |
| 阵列共用 | **三层分时复用** | DSP 152 → 64，是 Lab8 能塞进 7020 的关键 |
| **数据通路** | **一次 DMA 送 42 张（批处理）** | 每笔 DMA 有 ~76 µs 固定开销；批处理把它摊薄到 1/42，**端到端 75.85 → 11.6 µs/张**，且不改任何 PL 计算资源 |

**一句话**：准确率已到这套 INT8 权重的上限（与课程参考逐样本一致）、资源/功耗做到较优之后，最大的性能杠杆
不在 PL 内部（加快运算要翻倍 DSP，加权后抵消），而在 **PS↔PL 的传输方式**——
用批处理把 DMA 固定开销摊掉，是这次性价比最高的一步。

## 6. 批处理：本次最大的性能杠杆

### 6.1 问题定位

`dma_probe.py` 实测：同一笔 AXI DMA 传输，**8 字节与 520 字节耗时几乎相同**
（≈46 µs）。S2MM 同样有 ≈30 µs 固定开销。也就是说：

```
每张的端到端时间 = 固定开销(≈76 µs) + NPU 计算(≈10.7 µs)
B=1 时 75.85 µs/张，其中 88 % 是在等 DMA 的启动/寻址/中断
```

（46 + 30 > 75.85 是因为两个通道与 NPU 计算部分重叠，量级关系不变。）

### 6.2 解决办法

一次 DMA 传 N 张，把固定开销摊到 1/N。**难点在于 `tlast`**：
AXI DMA 的 S2MM 收到**第一个** `tlast` 就结束传输，如果 NPU 每张都拉 `tlast`，
S2MM 会在第 1 张就收工，结果整体滞后。

RTL 的做法：指令字 `[15:8]` 携带"本批剩余张数"，`fc_top` 内部维护计数器
`batch_left`，只在 `batch_left == 1`（本批最后一张）时产生 `output_data_last`。

```verilog
// 收到指令时装载
batch_left <= (cmd_reg[15:8] == 8'd0) ? 8'd1 : cmd_reg[15:8];
// 每次输出完成时递减
if (!mode_fmap && batch_left > 8'd1) batch_left <= batch_left - 1'b1;
// 只有最后一张才拉 tlast
byte_last = ~mode_fmap & (batch_left == 8'd1);
```

**注意 `batch_left` 的复位必须和它的载入/递减放在同一个 `always` 块（FSM）里**，
否则会被综合成 multi-driven net，最高位被常量顶掉，`tlast` 再也不产生。
这个坑我们踩过，详见 [08 篇 §4](08_上板实测记录.md)。

### 6.3 收益

| 口径 | B=1 | B=42 | 提升 |
|---|---|---|---|
| 硬件传输（PS→PL→PS） | 75.85 µs/张 | **11.38 µs/张** | 6.6× |
| 含 cache 维护 | ≈76 µs/张 | 19.86 µs/张 | 3.8× |
| 含脚本数据准备（改造前） | 722.5 µs/张 | 35.01 µs/张 | 20.6× |

**PL 资源零代价**：DSP/BRAM 完全不变，只多了 25 个寄存器和少量组合逻辑
（整机 LUT 增量 < 0.1 %）。

### 6.4 PS 侧同时做的四处优化

| 改动 | 依据 | 效果 |
|---|---|---|
| `BATCH` 1 → 42 | 见 6.1 | 硬件 75.85 → 11.59 µs/张 |
| 样本 numpy 预排 + `np.copyto` | 逐张 `in_buf[:] = bytearray` 填 21 KB 要 155 µs | → 51 µs |
| SA/DA 寄存器只在缓冲区变更时写 | 单次 AXI-Lite 寄存器写实测 **4.4 µs**，原每笔写 6 次 | 每笔 6 写 → 2 写 |
| `.coe` 改字符级 numpy 过滤 | 逐 token `strip()/set()` 解析 21 504 个 token 要 360 ms | 361 → 179 ms |

> 脚本总耗时约 2 s，其中 1.7 s 是加载 4 MB 比特流、0.18 s 读样本，
> **真正推理只有 0.5 ms**；`time python3` 看到的 12 s 里约 10 s 是 `import pynq`。

## 7. 如果要冲时间分：推荐的组合

按性价比排序：

| 步骤 | 工作量 | 收益 | 风险 |
|---|---|---|---|
| ① 地址寄存器 `max_fanout` 复制 | 半天 | Fmax 107→130+ MHz | 低 |
| ② 收样本流水化 | 半天 | −63 拍 | 低 |
| ③ FCLK 提到 125 MHz | 1 小时（改 BD） | 再省 20 % | 中（要重跑时序） |
| ④ 阵列扩到 128 车道 | 2~3 天 | 时间减半 | **高**（全链路重验） |

**①②③ 做完**：约 `(1339−127) × 8 ns = 9.70 µs`，接近参考实现的 7.585 µs。
**再加 ④**：约 5.5 µs，可以超过参考实现，但 DSP 翻倍。

> 课件第 22 页也在讲这件事："翻转率更低、功耗更低，但面积更大"——
> 硬件设计里没有免费的午餐，能说清**为什么这么选**比单纯跑得快更重要。

## 8. 与另一种实现的差距：40 DSP / 5 µs / 100 %

有同学参考华为 CANN 的思路做出了 **40 个 DSP、约 5 µs、100 % 准确率** 的方案。
我们的数字是 64 DSP、9.152 µs、88.10 %。这一节把差距算清楚，供答辩时正面回应。

### 8.1 先做算术：40 DSP 怎么可能跑到 5 µs

三层全连接的 MAC 总数是固定的：

```
FC1 512×128 = 65,536
FC2 128×32  =  4,096
FC3  32×2   =     64
合计          69,696 次乘加
```

我们实测 1144 拍 × 64 DSP @125 MHz，即 **0.95 MAC/DSP/cycle**（利用率 95 %）。
按这个模型倒推对方：

| 每 DSP 每拍 | 40 DSP 的时间 @125 MHz | 要压到 5 µs 所需时钟 |
|---|---|---|
| 1 MAC（我们的做法） | 13.94 µs | 348 MHz |
| 2 MAC | 6.97 µs | 174 MHz |
| **3 MAC** | **4.65 µs** | **116 MHz** |
| 4 MAC | 3.48 µs | 87 MHz |

**只有"一个 DSP 一拍做 3 次乘加"这一档，能在 125 MHz 附近落到 5 µs。**
反过来说：如果对方是 40 路平铺、一 DSP 一乘加，时间是 13.9 µs，比我们还慢 50 %。

### 8.2 3 MAC/DSP 要求权重是 4 bit

DSP48E1 的资源是 A 口 25 bit、B 口 18 bit、乘积 48 bit。
4 bit 权重 × 8 bit 激活 = 12 bit 乘积，48 / 12 = 4 个字段（不留保护位），
留保护位实用 3 个。所以"3 路打包"和"4 bit 权重"是同一件事的两面。

这同时解释了另外两个数字：

| 现象 | 解释 |
|---|---|
| 40 DSP（比我们少） | 3 路打包 → 等效 120 MAC/拍，只需 40 个 DSP |
| ~5 µs | 69,696 / 120 = 581 拍 @125 MHz = 4.65 µs |
| 100 % 准确率 | 4 bit 必须靠 **QAT（量化感知训练）**，不是截位 |
| 1.5 W | DSP 少一半，动态功耗自然低 |

> **关键区别**：我们做的 4 bit 是"把 8 bit 训练好的权重截到 4 bit"，必然掉精度（42 张里 27 张平局）；
> 对方是"按 4 bit 重新训练"，可以几乎不掉。同一句话"4 bit"，含义完全不同。

### 8.3 CANN 能被借用的是这四件事

| CANN 的概念 | 对应到 FPGA | 对我们的意义 |
|---|---|---|
| AMCT 量化工具（QAT） | 4/8 bit 量化感知训练 | **100 % 准确率的来源，不是硬件** |
| Cube 阵列 | 多通道一拍的乘加结构 | 即"打包"，提升单位 DSP 吞吐 |
| 多级缓冲 / Tiling | L1/L0 buffer、分块调度 | 提高利用率、藏访存延迟 |
| 数据复用（权重驻留） | 权重锁在片上反复用 | **可能解释对方 BRAM 比我们省**（我们 45 %） |

最后一条值得注意：我们每拍都从 1024 bit 宽的 BRAM 里读权重，BRAM 用掉 45 %；
CANN 式设计把权重驻留复用，BRAM 需求低得多。

### 8.4 差距的性质：架构代差，不是实现质量

| 维度 | 我们 | 对方（推断） |
|---|---|---|
| 权重精度 | 课程给定 INT8 | 4 bit（QAT） |
| 每 DSP 吞吐 | 1 MAC/cycle（利用率 95 %） | 3 MAC/cycle |
| 权重复用 | 每拍读 BRAM | 片上驻留 |
| 结果 | 64 DSP / 9.15 µs / 88.1 % | 40 DSP / ~5 µs / 100 % |

**我们在"一 DSP 一乘加 + 8 bit"这个档次里已经接近上限**（MAC 利用率 98 %），
差距来自精度档次与打包技术，而不是实现没写好。

### 8.5 为什么本次没有追这条路

1. **QAT 需要训练环境**：课程只给了 INT8 权重和 `.pth`，没有训练脚本与数据管线；
   自己搭 PyTorch 量化感知训练至少一周起，且不保证复现对方的 100 %。
2. **打包数据通路是全新的验证面**：3 路打包的符号位、字段间进位、饱和处理，
   任一处错都是"结果错但不报错"——我们已经踩过 `batch_left` 那类坑。
3. **42 个样本的 100 % 证据力有限**：样本少，过拟合风险高。

### 8.6 答辩口径

> 我们知道有同学参考 CANN 的思路，用 4 bit QAT + 每 DSP 三路打包做到了 5 µs / 40 DSP。
> 我们的方案是课程给定的 INT8 权重 + 一 DSP 一乘加，在 64 路配置下 MAC 利用率 98 %，
> 已经接近这个架构的上限；差距在精度档次与打包，不在实现质量。
> 如果重做，第一优先级是 QAT 降到 4 bit，第二才是打包。
