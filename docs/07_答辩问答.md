## A. 系统级（Lab8）

**A1. 一句话说清你们做了什么？**
PS 通过 AXI DMA 把 512 字节样本经 AXI-Stream 送进 PL，PL 里的 NPU 完成三层全连接推理，
再把 1 字节分类结果（或 162 字节特征图）经 AXI-Stream 送回 PS。42 张图 88.10 %；
一次 DMA 送 42 张，端到端 **11.6 µs/张**（PL 内部计算 1339 拍）。

**A2. 为什么要两个工作模式？**
课件第 6 页的要求。推理模式验证"分类能力"，特征图模式验证"中间层算得对不对"——
后者是调试和答辩时证明设计正确性的关键手段（能看到每层输出，而不只是一个 0/1）。

**A3. 特征图模式为什么不重新推理？**
三层结果本来就存在 `fc1_out_ram` / `fc2_out_ram` / `fc3_hold` 里，推理结束后仍然保留。
特征图模式只是**换一个地址去读**，不经过运算单元。

**A4. 两个时钟域怎么处理的？**
AXI 域（`s_axis_aclk`）和计算域（`fc_clk`）各一个异步 FIFO（格雷码指针 + 双触发器同步）。
输入 FIFO 64bit×512，输出 FIFO 65bit×512（多 1 位存 `tlast`）。
仿真里用 100 MHz / 150 MHz 验证过真跨域。

**A5. DMA 的 tlast 怎么保证？**
`fc_top` 多一个 `output_data_last` 输出，随最后一个字节一起有效；
打包级把它连同数据一起写进 65 位 FIFO，AXI 侧直接取 FIFO 的最高位当 `tlast`。

**批处理时的关键是"整批只拉一次 tlast"**：S2MM 收到第一个 `tlast` 就结束，
所以如果每张都拉，42 张只会收到第 1 张。我们让指令字 `[15:8]` 携带"本批剩余张数"，
`fc_top` 用 `batch_left` 计数器，只在减到 1 时产生 `output_data_last`。
仿真验证过 4 包连发和 12 包突发（780 拍 > FIFO 深度 512），实板 42 张一次传输结果全对。

**A5b. 为什么要批处理？**
实测每笔 AXI DMA 传输有约 **46 µs MM2S + 30 µs S2MM 固定开销**，
和 8 字节还是 520 字节几乎无关（`dma_probe.py` 的结论）。逐张模式 75.85 µs/张里
近 9 成在等 DMA。42 张合并成一笔后 **11.6 µs/张**，PL 资源零代价
（只多 25 个寄存器和少量逻辑，LUT 增量 < 0.1 %）。

**A6. S2MM 怎么知道收多少？**
简单模式（非 SG）下由 PS 侧 `recvchannel.transfer(buf, nbytes=...)` 指定：
推理 8 字节、特征图 168 字节（21×8，最后 6 字节是补 0）。

**A7. 为什么输出要打包成 64bit？**
AXI DMA 的流宽度配的是 64bit（和 Lab1 一致）。NPU 一个字节一个字节出，
所以要有个打包级把 8 个字节拼成一个字。也可以把 DMA 配成 8bit，
但那样 162 字节就要 162 拍，DMA 效率低。

**A8. 综合日志里有 `s_axis_tkeep` 的告警，是接口悬空了吗？**
不是。**整机综合后没有任何悬空接口**：`design_1_wrapper` 这一层，BD 把 `pl_fc_top` 的
每个 AXI-Stream 端口都连到了 smartconnect 和 DMA，顶层 `synth_1` 日志里没有相关告警。

会报的是 **IP 单独做 OOC 综合**时的那 16 条
`[Synth 8-7129] Port s_axis_tkeep[n] ... has no load`——意思是"端口有连接、模块内部没有负载"。
因为输入是**定长协议**：65 拍 × 8 字节全有效，tkeep 恒为 `8'hFF`；
NPU 自己数满 64 个字就知道包结束，不需要 tlast。所以内部没用它们，综合器就优化掉了。

**最硬的依据**：课件第 14 页让我们参考的 **Lab1 `axis_rd_interface.v` 完全相同**——
它的 tkeep/tlast 也只声明不使用。所以这个现象和参考实现一致。

（输出侧则必须用 tlast，课件第 9/13 页明确要求，我们用一个 65 位 FIFO 把
`{last, data}` 一起跨时钟域来实现。详见 01 篇 §4.4。）

## B. 架构与数据通路（Lab4–Lab5）

**B1. 为什么用 64 路并行？**
一条加法树吃 64 个乘积，正好覆盖一个输入组（fc1 的 512 维分 8 组）。
再往上加就要 128/256 个 DSP，资源和功耗都会涨。

**B2. 三层的延迟链为什么能统一？**
因为 Lab6 截位后三层都是 8×8 乘法（`L_MULT = 3`）、都用 64 输入加法树（`D_TREE = 6`）、
都用同配置的 BRAM（`L_RAM = 3`），所以 `T_PRE = 12`、`DLY_OUT = 15` 对三层都成立。

**B3. `L_RAM = 3` 是怎么来的？**
Lab4 实测的。`.xci` 里写 `C_READ_LATENCY_A = 1`，但 xsim 行为模型的真实延迟是 3——
信文档就全错。方法：先只跑第一层，拿参考文件比对，反推这个常数。

**B4. 一个累加器够吗？**
够。`out_channel` 只在 `group_idx` 回绕那一拍 +1，所以同一通道的各组是连续到达的，
一个寄存器就够（这是 Lab4 就定下的"单累加器不变量"）。

**B5. 为什么 fc3 不用 BRAM？**
只有 2 个输出通道，锁在寄存器里更省。

**B6. 加法树的位宽怎么定？**
两个 W 位有符号数相加一定装得下 W+1 位，所以每级 +1 位。64 输入 6 级，
顶层 16+6 = 22 位，再符号扩展到 32 位。**全程不截位，是精确值。**

## C. 截位与量化（Lab6）

**C1. 8bit 的移位量 10/9/8 怎么来的？**
`SH = bit_length(该层实算最大绝对值) − (8−1)`。
fc1: 80805 → 17 位 → 10；fc2（用已截位的 fc1 实算）: 37683 → 16 位 → 9；
fc3: 32166 → 15 位 → 8。

**C2. 为什么每层都要重算，不能直接用三层的原始最大值？**
原始最大值是"前面层不截位"时的统计。第 1 层截位后，第 2 层实际最大值只有 37 683，
和原始的 39 386 422 差三个数量级。用原始值定移位量会严重过移，把结果压成 0。

**C3. 课件写第 2 层移 8 位，你们写 9 位，谁对？**
更正版课件（`Lab6 (1).zip`）已经改成 9。移 8 位会让 37 683 变成 147，
超过 8bit 有符号上限 127，溢出成负数。这是可以算出来的硬约束。

**C4. 截位是组合逻辑还是流水级？**
纯组合的位选择（`>>>` 综合出来就是连线），不加流水级，所以 `DLY_OUT` 不变。

**C5. 4bit 准确率只有 50 %，是不是设计错了？**
不是。RTL 与 Python 模型 13 608 个值逐值一致。50 % 是"27 个平局 + 平局一律判 1"造成的，
换成"平局判 0"就是 85.7 %。**准确率在这里取决于判据，不是网络。**
旁证：4bit 下 15 个非平局样本**全部判对**。

**C6. 为什么 8bit 能做到零损失？**
8bit 量程 ±127，而三层截位后实际只用到 [0,78] / [0,73] / [-126,76]，
留有余量；fc3 仍保留 `10 vs -11` 的清晰区分度，判别边界没翻转。

**C7. 准确率 88.1 % 还能提高吗？**
能，但不是靠调截位——**未截位网络也是 37/42**，88.1 % 是原始 INT8 模型的上限。
要提升必须重新量化训练（课件提供的 `.pth` 原始模型是 FP32、100 %）。

## D. 数据流控制（Lab7）

**D1. 为什么状态机要 9 个状态？**
两条支路在 `FC3_out` 汇合，前面不重叠：推理走 `data_receive → FC1 → FC2 → FC3`，
特征图走 `FC1_out → FC2_out`。合并会丢掉"当前是在算还是在读"的信息。9 个状态也是课件参考图的划分。

**D2. 同一个 BRAM 既写又读会不会冲突？**
不会。写只发生在 `FC1`/`FC2` 状态，读发生在 `FC2`/`FC3`/`FC1_out`/`FC2_out` 状态，**互斥**。
读书时 `wea` 强制为 0，从结构上消除同拍读写隐患。

**D3. BRAM 读延迟三拍怎么藏？**
整行读 + 移位输出：两行地址提前一拍连续发出，各自在第 3/4 拍锁存，
从第 5 拍开始满速 1 字节/拍。延迟只影响开头 5 拍。

**D4. 输出 FIFO 满了怎么办？**
字节计数器停住，同一个字节下一拍重试。因为写使能是"判断 `!full` 之后才置位"，
最多写满、不会溢出。

**D5. `GROUPS=1` 那个坑是什么？**
fc3 的组数只有 1，`(group_idx_dly == GROUPS-1)` 恒为真，空闲时 `wren` 会一直为高、
每拍吐垃圾。修法是另跟一条 `running` 延迟链来门控。

## E. 验证

**E1. 你们怎么证明设计是对的？**
三层证据链：官方参考文件 ↔ Python 独立模型 ↔ RTL 仿真 ↔ 上板。
Lab6 里 RTL 与 Python 模型 **13 608 个值逐一相同**，两个位宽各一套。

**E2. 最硬的证据是哪条？**
`fc1_w4[i] == fc1_w8[i] >> 4` 对全部 5 376 个值成立。
4bit 与 8bit 的 fc1 输入权重完全相同、只有 `SH1` 不同（14 vs 10），
这个关系不成立就说明 4bit 没真正生效。

**E3. 你们踩过哪些"不报错但结果错"的坑？**
① 加法树符号扩展缺失（负数全算成正的大数）；
② 车道约定混用（老师给的 coe 是 MSB 优先，自己生成的是 LSB 优先）；
③ 综合 run 上残留的 `-generic` 覆盖了 wrapper 参数；
④ Lab8 的 testbench 把输入字节序写反；
⑤ **`batch_left` 多驱动**：复位写在"输出数据寄存器"那个 `always` 块、
载入/递减在 FSM 块里，综合报 `Synth 8-6859 multi-driven net`，
最高位被常量顶掉 → `tlast` 永不产生 → S2MM 挂死。**仿真完全正常**。

前四条靠"逐值比对"抓到，第五条只能靠读综合日志里的 CRITICAL WARNING 抓到。
经验：**改完 RTL 必须翻一遍综合日志的 warning**，不能只看 `SYNTH OK`。

**E4. 仿真环境有什么特别注意的？**
- 混合语言：`mult_gen` 只有 VHDL 模型，BRAM 是 Verilog；
- BRAM 仿真读 `.mif` 不读 `.coe`，要拷进运行目录；
- Git Bash 下 GUI 的 `launch_simulation` 会 Broken pipe，改用命令行 `xvlog/xelab/xsim`。

## F. 性能与优化

**F1. PL 内部 1339 拍花在哪？**
FC1 占 77.8 %（1042 拍）；收样本 192 拍占 14.3 %、FC2 6.1 %、其余很少。合计 1339 拍。

**F2. 怎么把端到端时间降下来？**
**先分清两件事**：
- **PL 三层计算**只有 9.152 µs（1144 拍 @125 MHz，整包含收发为 1339 拍、10.712 µs）；
- **端到端 PS→PL→PS** 在逐张模式下要 75.85 µs，因为每笔 DMA 有 ~76 µs 固定开销。

所以收益最大的不是"让运算更快"，而是 **批处理**：42 张一次传，11.6 µs/张。
其次才是：频率 100→125 MHz（−20 %）、收样本流水化（−127 拍）、128 车道（时间减半但 DSP 翻倍）。

**F3. 那为什么不直接上 128 车道？**
DSP 从 64 涨到 128（29 % → 58 %），面积和功耗都涨。
评分里时间、资源、功耗各占 25 %，**翻倍 DSP 换一半时间，四项加权后基本抵消**，
但风险和重验成本很高（延迟链、加法树、打包全要改）。
而批处理是**纯 PS 侧改动 + 25 个寄存器**，收益 6.6 倍——性价比完全不同。

**F4. 关键路径是什么？**
`fc_top` 状态机（one-hot `state_reg[7]`）→ 乘法阵列 DSP 的 B 口，4 级逻辑，7.6 ns。
**最早的瓶颈不是它**：未优化时是 `fc2/weight_addr_o → BRAM 地址`，逻辑级数 0、布线占 95 %
——宽 BRAM（1024bit × 15 列）的地址扇出。加 `(* max_fanout = 8 *)` 让工具复制寄存器后，
这条路径消失，瓶颈才转到状态机→DSP。

**F5. 功耗怎么控制？**
少用 DSP（64 个）、三层共用阵列、两个时钟域同源（实际只有一棵时钟树）、
FIFO 去掉复位清零（否则 6.6 万个触发器）。
125 MHz 比 100 MHz 多 3.1 % 功耗，换 20 % 时间，净收益为正。

**F6. BRAM 用了 45 %，能降吗？**
能。现在是被**位宽**吃掉的（1024bit 宽 × 15 列），不是容量。
改成 512bit 行宽能降到 ~30 个 tile，但要改地址映射和打包逻辑。

**F7. 你们的时间指标怎么报？**
三个口径，说清楚就不会被打：
- **11.6 µs/张**：42 张一次 DMA 的硬件传输时间，体现设计能力；
- **19.9 µs/张**：加上 `flush` / `invalidate` 的 cache 维护；
- **34~35 µs/张**：再算上脚本里 21 KB 的数据准备（可继续优化）。

**F8. 为什么 100 MHz 版和 125 MHz 版跑出来一样快？**
因为 BD 里设的 FCLK **只决定时序约束，不改变板上真实频率**——Zynq 的 PS 时钟
由启动时 FSBL 配置。实测两版分别是 11.586 和 11.538 µs/张。
125 MHz 版的真正价值是**按真实频率做了时序签核**（WNS +0.403 ns）；100 MHz 约束下
的 +0.746 ns 意味着关键路径 9.25 ns，在真实频率下其实不满足。

## G. 开放题（老师爱问）

**G1. 如果要把网络换成卷积网络，架构要改什么？**
乘法阵列和加法树可以复用；要加的是"滑动窗口"的地址生成、行缓冲（line buffer）、
以及权重复用策略。状态机要加卷积层/池化层的状态。

**G2. 如果要支持多 batch？**
输入 RAM 从 4 行扩到 `batch × 4` 行，地址加 batch 偏移（Lab6 就是这么扩到 42 样本的）。
但吞吐不会变，因为计算阵列还是被一层占满。

**G3. 为什么不用 HLS？**
课程要求手写 Verilog。而且手写能精确控制流水线级数和位宽，
这在"延迟链对齐"这种场景里是必需的——HLS 很难保证 15 拍这种精确时序。

**G4. 这个设计最大的遗憾是什么？**
推理时间比参考实现慢 1.8 倍。根因是 fc1 的并行度只有 64 路。
如果重来一次，会在 Lab5 阶段就把阵列做成参数化的 64/128 双模式，
这样 Lab8 只需要改一个参数就能切换性能/面积。

**G5. 团队分工怎么讲？**
建议按"数据通路 / 控制与接口 / 验证与文档"三条线分，
每个人都能说清自己模块的**设计依据 + 踩过的坑 + 验证方法**——
比"我写了 fc1.v"这种回答有说服力得多。
